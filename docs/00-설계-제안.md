## 2. 목표 아키텍처 (추천안)

### 2.1 단일 Next.js 15 앱 + 라우트 그룹

```
abcde/
  src/app/
    (public)/               허브. 로그인 없이 열람
      page.tsx              /            랜딩: 소개 + 프로젝트 카탈로그 + 최근 글
      projects/             /projects, /projects/[slug]   프로젝트 소개·아키텍처·데모
      notes/                /notes, /notes/[slug]         Field Notes(블로그, MDX)
      about/  contact/  privacy/
    (auth)/                 /login /signup /auth/callback /account /pending(승인 대기)
    (apps)/
      aidapel/              /aidapel/lobby, /aidapel/test/p1…, /aidapel/teacher/…, /aidapel/admin
      aieewa/               /aieewa/generate, /aieewa/evaluate
    (admin)/admin/          사용자 승인·역할·앱 권한·사용량
    api/
      aidapel/…  aieewa/…  admin/…     (모두 인증 + 권한 + 한도 검사)
  src/apps/aidapel/         앱별 컴포넌트·lib (모듈 경계, 서로 import 금지)
  src/apps/aieewa/
  src/lib/                  공용: supabase(client/server/admin), auth 가드, 사용량·한도, LLM 클라이언트, 디자인 토큰
  src/content/
    projects.ts             ★ 프로젝트 레지스트리 — 항목 하나 추가하면 카탈로그·내비·권한 게이트가 자동 반영
    notes/*.mdx             블로그 글
  supabase/migrations/      통합 스키마 (hub_* 공용 + 앱별 테이블)
  docs/                     설계·운영 문서
```

**왜 단일 앱인가.** 같은 프레임워크, 같은 DB 제품, 작은 팀(1인). 세션 쿠키·디자인 토큰·권한 가드를 한 번만 만들고 모든 앱이 공유한다. 모노레포(앱 여러 개)는 빌드·배포·세션 공유가 모두 배가 되고, 지금 규모에서 얻는 것이 없다.

**대안.** (a) 모노레포 + 앱별 배포 + Vercel 멀티존 — 앱이 5개 이상이고 팀이 나뉠 때 유효. (b) 허브만 새로 만들고 기존 배포로 링크 — 가장 빠르지만 로그인 통합·디자인 통일이 불가능해 "통합"이 아니다.

### 2.2 프로젝트 레지스트리 (확장 지점)

```ts
// src/content/projects.ts
{
  slug: 'aidapel', name: 'AIDAPEL', title: 'AI 초등영어 기초학력 진단 플랫폼',
  kind: 'integrated',            // integrated | external | article
  status: 'active',              // active | archived | wip
  access: { view: 'public', use: ['teacher','student'] },   // 소개는 공개, 사용은 역할 필요
  entry: '/aidapel/lobby', repo: 'https://github.com/bmm0465/AIDAPEL',
  tags: ['DIBELS','STT','LLM'], year: 2025,
}
```
새 프로젝트를 추가할 때: 레지스트리에 항목 1개 + `src/app/(apps)/<slug>/` 라우트 + `src/apps/<slug>/` 코드 + 마이그레이션. 그 외(내비, 카탈로그 카드, 소개 페이지 골격, 권한 게이트)는 자동.

### 2.3 인증·권한·비용 통제

- **인증**: Supabase Auth, `@supabase/ssr` 표준 패턴(서버에서 `getUser()`/`getClaims()`; 미들웨어는 세션 갱신 + `(apps)`·`/api/(aidapel|aieewa)` 보호).
- **역할**: `profiles.role ∈ {admin, teacher, student, guest}`.
  - `guest` = 가입만 한 상태. 둘러보기·데모·읽기만 가능. 유료 API 호출 불가.
  - `teacher` = 관리자가 승인. 도구 사용 가능.
  - `student` = 교사가 일괄 생성(AIDAPEL 방식 유지). 배정된 평가만 응시.
  - `admin` = 승인·역할·사용량 관리.
- **앱 단위 권한**: `app_access(user_id, app_slug, granted_by, granted_at)` — 역할만으로 부족할 때(특정 교사에게 AIEEWA만 열기 등).
- **비용 통제**: 모든 LLM/STT 호출은 서버 라우트에서만, 키는 서버 전용. `usage_events(user_id, app, provider, model, tokens_in, tokens_out, est_cost, created_at)` 기록 → 사용자별 **월 한도**(기본값 예: 교사 1인 월 $5) 초과 시 차단, 관리자 화면에서 조정. 단순 속도 제한(분당 N회)은 Postgres 기반으로 구현(외부 서비스 불필요).
- **가입 정책 선택지**: ① 가입 자유 + 관리자 승인 후 사용(추천) ② 초대 링크 전용 ③ 가입 자유 + 개인 API 키 입력(BYOK) ④ 가입 자유 + 월 한도만.

### 2.4 데이터베이스

**추천: AIDAPEL의 Supabase 프로젝트를 허브 DB로 채택**하고 AIEEWA 테이블을 추가한다.
- 이유: AIDAPEL에 이미 실제 사용자(학생·교사·관리자)와 결과·음성 데이터가 있다. 이 데이터를 옮기는 것이 가장 위험하고, AIEEWA 데이터(문항·청크)는 작아서 옮기거나 재생성하기 쉽다.
- 할 일: `user_profiles` → 허브 `profiles`로 확장(role에 guest 추가, 승인 상태 컬럼), `app_access`·`usage_events` 추가, AIEEWA 스키마(`questions`, `student_answers`, `documents`, `document_chunks` + pgvector)를 `aieewa_` 접두어로 추가, RLS 재정비.
- 대안: 새 Supabase 프로젝트를 만들고 둘 다 이전(AIDAPEL은 이미 `scripts/migrate-*.ts`와 이전 가이드가 있어 가능하지만 이중 작업), 또는 프로젝트 2개 유지(로그인 2번 → 비추천).

### 2.5 디자인

- **LOOP 디자인 시스템 계승**: Pretendard, 따뜻한 회색 표면 4단계, 선(hairline)으로 위계, 액센트 1색, 그라데이션·글래스·장식 애니메이션 금지, ESLint로 강제. 한글 타이포 규칙(`word-break: keep-all`, 행간 1.7, 굵기 400/500/600).
- 허브 셸(내비·푸터·카탈로그·글)부터 적용. 두 앱의 내부 화면은 **1차에서 그대로 이식**(동작 보존) → 2차에서 셸 스타일로 점진 교체. 두 앱 모두 인라인 스타일 위주라 한 번에 바꾸면 회귀 위험이 크다.
- github.io의 다크 슬레이트/글래스 스타일은 계승하지 않는다(LOOP 문서가 명시적으로 배제한 문법). 태그라인·문구·글은 그대로 가져온다.

### 2.6 배포·도메인

- Vercel 새 프로젝트 `abcde` ← GitHub 저장소 연동(푸시 시 자동 배포). Vercel CLI는 미로그인 상태라 대시보드에서 연결하는 편이 빠르다.
- 도메인: 초기 `abcde-projects.vercel.app` → 이후 커스텀 도메인(예: `abcde.kr`) 연결 가능. 결정은 미뤄도 된다.
- 이전 완료 후: `aieebss.vercel.app` → `/aidapel` 리다이렉트, `bmm0465.github.io` → 허브 링크(또는 리다이렉트).

## 5. 놓쳤을 수 있는 지점

### 5.1 보안
1. **AIEEWA API 무인증** — 허브에서는 LLM·STT·DB 쓰기 라우트 전부에 인증 + 역할/앱 권한 + 월 한도 + 속도 제한을 건다. 예외 없음.
2. **디스크의 평문 자격증명** — `Dev/교사 계정.txt`, `Dev/aieebss/학생_이메일_비밀번호_목록.csv`, 학생 계정 양식 CSV 3개. git에는 없지만 평문이다. 내용은 읽지 않았다. 안전한 곳(비밀번호 관리자)으로 옮기고 파일 삭제, 가능하면 해당 비밀번호 순환 권고.
3. **`Access-Control-Allow-Origin: *`** (AIDAPEL `vercel.json`, `/api/*`) — 불필요. 제거.
4. **서버 로그의 개인정보** — 페이지·API에서 `console.log`로 이메일·ID 출력. Vercel 로그에 남는다. 제거.
5. **`X-XSS-Protection`** 은 구식. CSP(Content-Security-Policy)로 대체하고 `frame-ancestors 'none'`.
6. **Supabase 클라이언트의 "디버깅용" 설정** (`persistSession:false`, `autoRefreshToken:false`, `flowType:'implicit'`) — 인증이 불안정해지는 원인. 표준 SSR 패턴으로 재작성.
7. **미들웨어 `getSession()`** — 토큰 검증을 안 한다. `getUser()`/`getClaims()`로.
8. **저작권** — 교과서 PDF는 절대 저장소에 넣지 않는다(RAG 코퍼스는 DB에만). AIDAPEL `public/audio/…/chunjae-text-ham/`(출판사 음원)도 공개 저장소 적재가 적절한지 확인 필요.
9. **미성년자 데이터** — 학생 이름·음성 녹음은 민감정보. 개인정보처리방침, 보관 기간, 삭제 요청 경로, 교사 동의 절차 페이지가 필요하다. 로컬 `exports/*.xlsx`(학생 결과)도 관리 대상.
10. **관리자 하드코딩** (`shim@abs.com` in migration) — 환경변수 또는 DB 관리로.
11. **가입 개방 시 봇** — 이메일 확인 필수 + 승인제로 실질 차단. 필요 시 Cloudflare Turnstile.
12. **service role 키 사용 범위** — 관리자 라우트·시드 스크립트로 제한. 일반 라우트는 사용자 세션 + RLS.

### 5.2 UX
1. **방문자 유형 3종에 맞춘 진입** — 비로그인 방문자(둘러보기·데모·글), 승인된 교사(도구), 학생(배정된 평가). 로그인 후 역할별 랜딩.
2. **로그인 없이 볼 수 있는 것 최대화** — 프로젝트 소개, 아키텍처 다이어그램, 결과 화면 캡처, 샘플 문항·피드백(정적), 개발 보고서·사용자 가이드. "써보고 싶으면 가입" 흐름.
3. **승인 대기 상태 설계** — 가입 직후 "승인 대기" 화면, 관리자 대시보드 배지(+이메일 알림은 선택).
4. **상태 4종** — 로딩·빈·오류·권한 없음 화면을 공용 컴포넌트로.
5. **기기** — 학생 평가는 태블릿, 교사 대시보드는 데스크톱. 셸은 모바일까지 반응형.
6. **접근성** — 폼 라벨, 키보드 포커스, 대비 4.5:1, 오디오 컨트롤.
7. **앱 간 이동** — 상단 얇은 컨텍스트 바에 "ABCDE ▸ AIDAPEL ▸ 교사 대시보드" 식 위치 표시.
